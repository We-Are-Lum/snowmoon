## 2. The check: `npm run check:launch`

`scripts/check-launch.ts`. Read-only: it sends GETs, one POST to the sign-in start (below), and reads the database in a read-only transaction. It writes nothing on snowmoon.party, in the database or in git.

Run at **09:01 PT** from an up-to-date checkout of `main` (after `git fetch origin main` and checking out the deployed commit):

```
npm run check:launch -- --url=https://snowmoon.party
```

What it checks:

1. **The deployed commit** (`/api/version`), and that the code in your checkout (`src/lib/config.ts`, `src/lib/legal.ts`, `src/lib/challenge/`) is the same as that commit's. If not, it fails: its expectations would not be production's.
2. **/challenge is open**, from its served copy: "Entries close Sunday 22 November, 23:59 Pacific." Within 10 minutes of the open it retries up to four times, 30 s apart, for the 60 s cache.
3. **The six starting sheets**: each character's section on /challenge lists at least one sheet, and that sheet's page carries `challengeOpen: true` (the fork button a signed-in account sees, and the same switch that lets the publish gate through for a fork). It can't publish anything to prove the gate, so this is the page-side proof; the gate's logic is the same function (`challengeSheetsOpen`), tested in `npm run test:challenge`.
4. **The cap**: no public route serves it (the image status route doesn't include it), so the check computes it from the deployed code at this instant ($15 from 09:00) after step 1 has shown that code is production's; with `STUDIO_DATABASE_URL` in `.env.local` it also reads today's free spend as `studio_writer` in a read-only transaction and prints what's left.
5. **Sign-in**: `POST /api/auth/web/start` answers 200 with a link on farcaster.xyz and a QR code. This opens a five-minute channel on Farcaster's relay, exactly as tapping "Sign in" does; nothing is stored on snowmoon.party, and the channel token and link aren't printed. `--skip-signin` leaves it out.
6. **The bounties**: a poidh link for each character whose address is set, none for the others, and the amount in the bounty paragraph once set.

It also checks the launch kit's hand-written dates against `CHALLENGE.dates`. Exit 1 on any failure. `--no-db` skips the database.

**Dry mode**, no network: `npm run check:launch -- --at=2026-11-06T17:00:00Z` prints what the code expects at that instant (phase, the line /challenge should show, whether sheets are open to everyone, the cap, the bounties set, the kit dates). `npm run test:check-launch` tests it at the edges (08:59:59 and 09:00:00 PT on 6 Nov, the last second before the close and the close) and that it refuses a bad `--at`, `--at` with `--url`, and a missing target (46 checks, all passing on 2 Nov). `check:launch` is also on `test:check-targets`' list.

## 3. If something fails: what to switch off, and how

Every switch is in `src/lib/config.ts`, so **every switch is a commit on `main`**: a small PR, which the owner OKs and the agent merges (`gh pr merge --merge`); pushing to `main` deploys production. Then wait for `/api/version` to show the merge commit and run `check:launch` again.

| To stop | Change | Effect |
|---|---|---|
| Non-invited people making sheets | `CHALLENGE.openSheets: false` (`config.ts:455`) | Sheets are invited-only again at once; entries already made stay. **Privacy section 4 then promises more than the site does** ("During the remix challenge, anyone who passes … can publish a remix"): the owner decides whether that needs a reread in the same PR (legal texts describe today). |
| All image and view generation | `IMAGES.enabled: false` (`config.ts:470`) | The off switch for every Generate, sheet views and publishing (`api/designs` answers 503 "Publishing is switched off for now"). |
| The spend | lower `CHALLENGE.dailySpendCapUsd` (`config.ts:457`) | Takes effect on the next Generate. |
| Entries list / "Posted on" | `CHALLENGE.entries` / `CHALLENGE.posts` (`config.ts:448-449`) | Hides the list and counts / turns off adding posts. |
| Remix's Generate only | the env var `REMIX_GENERATE=off` (`config.ts:332`) | Not the challenge's images; listed because it's the one switch without a code change. |

**Revert or redeploy:**
- To undo a merge: a revert PR (`git revert -m 1 <merge commit>` on a branch), merged the same way.
- If a merge doesn't deploy, or after changing an env var in Vercel: redeploy the **current production deployment**, `~/.npm-global/bin/vercel redeploy <its URL> --scope nates-projects-d1780cff`. **Never `vercel --prod` from a working tree**: it would ship whatever that folder holds, not `main`. (`vercel rollback` also exists, but after a rollback Vercel stops promoting new production deployments automatically until one is promoted by hand: `docs/restore-point-2026-10-07.md`.)

**Who can do it:** the owner decides; the agent can prepare the PR and merge it once the owner says so. The Vercel commands need someone signed in to team `nates-projects-d1780cff` (the owner, or an agent on the owner's computer, where the CLI is signed in). Merging needs push rights on `We-Are-Lum/snowmoon`.

## 5. If X, then Y

| If | Then |
|---|---|
| **Sign-in is down** (the start route answers 502 "Farcaster sign-in is not answering", as Farcaster's relay did on 2 Nov) | It's Farcaster's relay or sign-in server, not the site: nothing to switch. Hold the posts and invites (they all need sign-in), retry `check:launch` every few minutes, and check whether signing in inside the Farcaster app (the miniapp signs in with Quick Auth, not through this relay channel; not tested here) still works. Post once a run passes. If it lasts, post with a line that sign-in is slow, or move the call's demo to the miniapp. |
| **The cap is reached** (Generate refused for "spend") | It resets at 00:00 UTC (16:00 PT). To raise it: a PR changing `CHALLENGE.dailySpendCapUsd`, the owner's decision on the amount. `check:launch` prints today's spend and what's left. Paid generations (wallet balance) have their own $25 cap and keep working. |
| **The prompt check refuses** sheet prompts as "unclear" | Anything but a clear "allow" is a refusal (`src/lib/images/guard.ts`); an empty answer, when the model runs out of tokens on a long prompt, is "unclear". Sheet views call the check with its default `maxTokens = 400` (`guard.ts:19`, from `src/lib/images/paid.ts:61,102`), while Remix uses 1,200 (`REMIX.guardMaxTokens`, `config.ts:325`). Short-term: suggest shorter sheet text (the limit is 600 characters). Fix: a PR passing a larger `maxTokens` for sheets (the owner's OK; it costs a little more per check). A refused Generate counts toward the person's daily 10. |
| **Neynar is down** | People outside the invited list can't generate at all (the gate fails closed), and a version published while Neynar doesn't answer is stored as "unchecked" and **never counts** as an entry, since eligibility is decided once at publish (`record.ts`, `rules.ts:87`). Invited people and admins are unaffected. Nothing to switch; tell people to wait before publishing. If versions were published during the outage, the owner decides whether they get a second look (there's no re-check today). |
| **A starting sheet is missing** | Before 09:00: publish it (an invited account or an admin). After 09:00: publishing one doesn't help, since /challenge lists only versions from before the open (`entries.ts:176`). Options, both the owner's call: a PR that lists sheets published by admins or the invited list at any time, or (worse: every post and the kit's dates would change) moving `opens`. Until then, people can still fork from the character's page on the site if a sheet exists there. |
| `check:launch` says the local code isn't the deployed commit | `git fetch origin main` and check out the commit `/api/version` shows, then run it again. |
| /challenge still says "Entries open" at 09:01 | The 60 s cache; the check retries for two minutes. If it still says so at 09:05, check `/api/version` and the server clock against the dates in the deployed commit. |
